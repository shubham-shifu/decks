Shifu Tasks · architecture review · pre-read

Cross-workspace tasks —
the data model decision
we need to make.

Shifu Tasks lets admins assign tasks across workspaces. The current two-task mirror system works for basic sync but breaks down when teams need shared comments, subtasks, and descriptions. This deck covers the problem and three approaches.

What works

Title, status, priority, due date, assignee all sync

Basic task metadata syncs bidirectionally between source and mirror tasks via LinkedTask.

What's broken

Comments, subtasks, description are completely isolated

Each workspace has its own copy. Teams can't collaborate — they're talking to themselves.

The decision

Three approaches — need your take on which to build

Query across linked tasks, single task with placement table, or a hybrid. Each has real tradeoffs.

01 — How it works today

Two tasks, linked by a record.
Metadata syncs. Everything else is isolated.

02 — Three approaches

Each solves the sharing problem differently.
Each has real tradeoffs.

Option A

Keep two tasks, query across the link

When loading comments/subtasks for a cross-workspace task, find the LinkedTask record, fetch from both task IDs, merge by timestamp.

pro Minimal schema changes. No migration.
pro Existing queries mostly untouched.
con Query complexity doubles for cross-workspace tasks.
con Edit/delete must cascade to both copies.
con Mention scope unclear — whose members show?
Option B

One task + TaskPlacement table

Single task in DB. Each workspace gets a TaskPlacement record with their own projectId, sectionId, and position.

pro One source of truth. No sync needed.
pro Comments, subtasks, description shared naturally.
con Big refactor — every query joins through TaskPlacement.
con Access control needs full rework.
con Migration of all existing tasks + placements.
Option C — Hybrid

One task, source keeps projectId, receiver gets TaskPlacement

Source task uses normal Task.projectId. Receiving workspace gets a TaskPlacement record for their own project/section placement.

pro Minimal disruption to existing queries.
pro Receiver can organize in their project.
pro Shared data naturally — one task.
con Two paths for placement — source vs receiver.
con Mention/assignment scope still needs solving.

The core tradeoff: Two tasks = workspace isolation but no shared data. One task = shared data but can't be in two projects. The hybrid tries to get both — one shared task for data, placement records for per-workspace organization.

03 — Questions for discussion

Eight decisions that shape
which approach we pick.

These are the unresolved design questions. The full architecture doc covers each in detail — this is the summary for our conversation.

Q1 Option A vs B vs C?
Which approach for sharing comments, subtasks, and description across workspaces?
Q2 Mirror task placement
Receiver MUST organize in their own project/section. Which approach handles this cleanly?
Q3 Mention scope
Shared comments — whose members appear in @mention dropdown? Current user's workspace, both workspaces, or only task participants?
Q4 Notification deduplication
Bidirectional sync can cause notification loops. Flag synced updates? Queue with dedup keys? Cooldown per task/user pair?
Q5 Description ownership
If shared, how to handle simultaneous edits? Last-write-wins, locking, or separate sections (requirements vs notes)?
Q6 Subtask assignee scope
Can Workspace A assign a subtask to Workspace B's members? Or only their own?
Q7 Cascade on deletion
Source task deleted — remove receiver's access, or soft-delete their placement? What about orphaned comments?
Q8 Performance at scale
Option A queries two task IDs for comments. Option B/C queries one. At what scale does this matter for us?
