No file boundaries

No agreement on who touches what. Merge conflicts are guaranteed, not occasional.

One giant commit

All his changes come as a single large commit. Hard to review, hard to merge partially, impossible to roll back one piece.

Sequential blocking

I can't start until the merge is clean

Functionality work is blocked until I've resolved every conflict. The merge step gates everything downstream.

02 — The proposed workflow

A daily sync, clear file ownership,
and a playbook for Ritik.

I'm creating a separate playbook deck for Ritik that covers this workflow and basic Git. Here's the plan.

New features

Ritik builds standalone HTML/CSS first

For any new page or component, Ritik designs it as a standalone HTML file — no framework, no imports, just pure UI. I port it into the real app with proper structure. Zero merge conflicts.

UI tweaks

File-level ownership, agreed daily

15-min morning sync. We agree on which files Ritik owns today and which are mine. No parallel edits on the same file. He pushes when done, I pull and build on top.

Result — Merge conflicts drop to near zero. Both of us work in parallel without blocking each other.
Git basics for Ritik

Small commits, proper messages, branch hygiene

Right now everything comes as one giant commit. I'll teach Ritik basic Git: commit often, write short messages, push completed work only. This makes reviews and rollbacks possible.

My own growth

Learning UI/UX design to reduce the handoff

Long-term, I want to handle end-to-end: frontend, backend, design, and infra. I'm learning from Ritik's work. Over time, the handoff friction naturally decreases.

03 — Better tooling, better planning

Claude Code has potential I'm not using yet.
And I need to plan work, not just react to it.

Claude Code usage

I have the tool but not the workflow

I'm using Claude Max but spending too much time on back-and-forth prompting. A session with someone who uses Claude Code daily — proper prompting patterns, planning before prompting, using agents for parallel work — would make a real difference.

Planning gaps

I'm saying yes to everything without scoping

First month energy. I'm taking on every task without pushing back or negotiating timelines. This leads to reactive work instead of planned work. I need to scope before committing.

The ask: A 1–2 session pairing with a senior engineer who uses Claude Code in a similar workflow — building full products end-to-end. Not a course. Just someone who can look at how I'm working and point out what I'm doing the hard way.

On saying no: I'm not going to start rejecting work. But I'll start giving honest estimates and flagging when something will push other things back. That's better for everyone than quiet overcommitment.
